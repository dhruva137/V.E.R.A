# Self-audit (Phase 0, 28 Sep 2026)

Before adding anything, we looked for our own mistakes. Numbers: `results/self_audit.json` and
`results/e2e_product.json`. Script: `experiments/self_audit.py`.

| # | Question | What we found | What changed |
|---|---|---|---|
| 0.1 | Does byte-identical code leak from train into evaluation? | Deduplication was per library, so shared code could cross splits: 0.17% of sealed rows, 0.13% of sealed-B, 0.89% of sealed-C and 1.3% of dev (mostly xxHash, which zstd bundles). Removing it moves sealed PR-AUC 0.7575 → 0.7577, sealed-B 0.5800 → 0.5804 and sealed-C 0.8412 → 0.8393. 34 byte-identical functions carry conflicting labels (small generic helpers). | **No material inflation.** The label noise is disclosed. Reported metrics are unchanged. |
| 0.2a | Is the prevalence manipulation applied so that exchangeability holds? | Positives are removed from the *test* side only. Calibration contains nulls only, so test nulls remain a random subset (grouped by source function) of the same null population. | Correct as run. Stated explicitly in the paper. |
| 0.2b | Does the guarantee hold when calibration comes from *other* libraries, as in deployment? | Our pooled studies split functions at random, so calibration and test shared libraries, which is favourable. New test: the **shipped** calibration (dev + sealed nulls, per ISA) against binaries built from library-disjoint sealed-B + sealed-C code. FDR ≤ 1.5% in all 6 cells (α = 0.1; m = 50/100/500; 5%/1%). Power 1.2%–8.7%. **But** non-crypto helpers *inside* Argon2 and libsodium exceed the calibration 95th percentile 17.5–22.2% of the time, where 5% is expected. | The guarantee held, conservatively, because most nulls (SQLite, libpng) sit *below* calibration. The Argon2/libsodium excess is a **measured exchangeability violation for non-crypto code inside crypto libraries**. It is disclosed as a limitation. Fix: add such helpers to calibration. |
| 0.3 | Is generalisation measured on enough libraries? | There were only 5 sealed crypto libraries. We registered **sealed-C** (BLAKE3, Argon2, tiny_sha3) before scoring it, for **8** in total. Pooled over sealed + sealed-B + sealed-C at O0–Os: ROC-AUC **0.820**, PR-AUC 0.662 (59,868 functions, 13,725 crypto). The per-library table is in the JSON. | Fixed. |
| 0.4 | Is the Findcrypt3 baseline fair? | All 4 of its "false alarms" came from `CRC32_poly_Constant`, a checksum rule that is correct by design. With crypto rules only: TPR 37.5%, **FPR 0%**. It finds **6/6** programs whose primitive has a constant in its database. V.E.R.A. finds 8 programs Findcrypt3 cannot (ML-KEM ×2, ML-DSA ×2, SipHash ×2, micro-ecc ×2). | The comparison is restated as **complementary**: Findcrypt3 names known constants, and V.E.R.A. certifies presence where there is no constant. |
| 0.5 | Is the shipped model the evaluated model? | It has the same feature list, and its sealed AUC (0.8266) matches the reported 0.8263. But research scripts *refit* v1 on differently ordered rows. The trees' internal early-stopping split then differs, so single-function scores differ by up to 0.39, though aggregate AUC matches to 0.001. The end-to-end "14/16" had been measured with such a refit. | **Re-measured through the product's own scan path** (`e2e_product.py`: `scan_blob`, shipped model and calibration). The result is unchanged: **14/16 crypto binaries, 0/14 false alarms**, 2 found only by the learned layer, 0.38 s median per binary (0.36 s when re-timed on an idle machine at 1e8639e). This file is now the source of every "as shipped" number. |

**Net:** no headline number was inflated. One measurement was taken on an equivalent-but-not-identical model;
it is now remeasured on the shipped artefact and unchanged. One new limitation is surfaced and quantified: non-crypto
helpers inside crypto libraries look crypto-like to the calibration.
